## 认证与安全

JWT 令牌在登录时签发，8 小时过期。所有接口（除 `/api/v1/health` 和 `/api/v1/auth/login`）需要在 Header 带 `Authorization: Bearer <token>`。

角色用 `@PreAuthorize` 方法注解控制。登出时将 token 加入内存黑名单（重启清空，靠 JWT 自身过期保底）。

安全头默认全开（X-Content-Type-Options, X-Frame-Options, CSP 等），可通过 `SECURITY_HEADERS_ENABLED` 关闭。

## BOSS 直聘能力边界

默认 BOSS_DEMO_MODE=true，所有 BOSS 端点返回 in-memory 静态样例数据（ConcurrentHashMap 存储，重启丢失）。

Flask 旧版有真实 boss-cli 子进程集成（通过浏览器 Cookie 登录），Java 版已预留配置项（BOSS_CLI_PATH、BOSS_DEMO_MODE=false），但未实测验证。迁移完整 BOSS 集成是待办项。

## 数据库 ER 概要

数据模型以 JPA 实体为核心，主要表包括：

- `users` — 账号（email/password/role/active）
- `jobs` — 岗位（title/jd_text/status/owner_hr_id）
- `recruitment_demand` — 招聘需求（关联 job）
- `candidates` — 候选人（name/email/phone/resume_json/owner_hr_id）
- `candidate_tag` — 候选人技能标签（多对多）
- `pipeline_stage` — 流程阶段记录
- `interview_feedback` — 面试反馈
- `interview_assignment` — 面试安排
- `interview_session` — AI 面试会话
- `offer_record` — Offer 记录
- `notifications` — 通知
- `audit_logs` — 审计日志
- `talent_map/company/person` — 人才地图
- `conversations/conversation_messages` — AI 助手对话

数据库迁移使用 Flyway，但脚本编号不全：缺 V1-V4、V6-V8。现有脚本从 V5 开始，接 V9-V18。这是因为 Flask 原型阶段和前几次重构产生的跳号。不影响运行，但迁移回滚时需要按实际内容操作，不要依赖编号连续性。

## 前端 types 迁移说明

联调改造期间，`frontend/src/types/index.ts` 全量字段从 snake_case 改为 camelCase（例如 `resume_json` → `resumeJson`）。`frontend/src/lib/api.ts` 做了三件事：

1. 响应信封解包（统一从 ApiResponse.data 取值）
2. 错误处理统一化（非 200 code 抛异常）
3. 23 条请求路径从 Flask 路由改为 Java 路由

改造范围覆盖 28 个页面 + 116 个组件 + 25 个 feature 文件，合计约 87 个文件。typecheck 0 错误，52 个契约测试全绿，npm run build 通过。

三个前端方法标注"Java 端暂未实现"：updateCandidateProfile、clarifyJob（具体方法名见 api.ts 注释），对应后端尚未实现的接口。

## 关键架构决策说明

### 决策：为什么选择 Spring Boot 3.2 + React 18 + PostgreSQL 16

- **Spring Boot 3.2**：LTS 版本，Java 21 虚拟线程支持，Spring Security 6 的授权架构改进。
- **React 18**：成熟的组件化方案，TypeScript 生态完善，团队有 React 经验。
- **PostgreSQL 16**：JSON 支持适合简历等半结构化数据存储，全文本搜索可替代 ES（当前阶段），无需额外的 License 成本。
- **被否决的方案**：Flask（性能瓶颈）、MongoDB（数据强关联）、SQLite（并发限制）。

### 决策：为什么认证用 JWT 而非 Session

- **JWT 优势**：无状态，适合前后端分离架构；无需 Redis/Session 存储；API 调试简单（直接传 token）。
- **权衡**：登出通过内存黑名单实现（重启清空），靠 JWT 自身 8h 过期保底。生产阶段可以引入 Redis 黑名单来持久化。
- **被否决的方案**：Session + Cookie（不适合 SPA + API 分离架构）、OAuth2（当前阶段过重）。

### 决策：为什么支付宝换 JPA 而非 MyBatis

- **JPA/Hibernate**：开发效率高，实体关系映射直接对应业务模型。适合 CRUD 密集、关联查询多的招聘系统。
- **权衡**：复杂统计查询（如 BI 聚合）使用 `@Query` JPQL 或原生 SQL 补充。性能瓶颈时可按 Controller 维度替换为 MyBatis 或 jOOQ。
- **被否决的方案**：纯 JDBC（开发效率低）、MyBatis（需要手写全部 SQL，关联多时冗余）。

### 决策：AI 能力三档降级策略

详见 AI 能力边界表。核心原则：**不因 AI 服务不可用而阻塞主流程**。LLM key 未配置时，AI 面试、简历解析、AI 助手全部自动降级，保证招聘专员可以正常走通"上传简历→匹配→推进→面试→Offer"全流程。

### 决策：为什么数据库迁移使用 Flyway 而非 Liquibase

- **Flyway**：基于 SQL 脚本，简单直接；与 Spring Boot 集成度好；版本控制直观。
- **权衡**：编号不连续（V1-V4、V6-V8 缺失）是历史原因——Flask 原型和前期重构产生的跳号。不影响运行，但回滚时需要按实际内容操作。
- **被否决的方案**：Liquibase（XML/YAML/JSON 配置学习成本高，不适合小团队）。
