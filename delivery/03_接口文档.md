# 接口文档补充说明

## 基准文档

完整接口定义见 `rebuild/backend-java/API.md`，共 105 个端点、19 个 Controller。本文仅补充 API.md 漏列的端点和差异说明。阅读前请先打开 API.md。

## 基础约定

- 基础路径：`/api/v1`
- 响应信封：统一 `ApiResponse<T>` 结构 `{ code, message, data, timestamp }`
- 认证：`Authorization: Bearer <token>`（除 `/api/v1/health` 和 `/api/v1/auth/login`）
- 分页：`?page=0&size=20`

## API.md 漏列的端点

### BiController（7 个补充端点）

API.md 只列了 overview / staff/{hrId} / job/{jobId} 三个。实际还有 7 个细分维度端点（同样在 `/api/v1/bi`）：

| 方法 | 路径 | 说明 |
|------|------|------|
| GET | `/api/v1/bi/funnel` | 招聘漏斗各阶段数量，参数 `?days=30`（可选 7/30/90） |
| GET | `/api/v1/bi/channel-quality` | 渠道质量分析，参数同上 |
| GET | `/api/v1/bi/interview-accountability` | 面试问责统计，参数同上 |
| GET | `/api/v1/bi/manager-alerts` | 管理者预警，参数同上，默认 90 天 |
| GET | `/api/v1/bi/demand-health` | 需求健康度，参数同上 |
| GET | `/api/v1/bi/resume-consumption` | 简历消费分析，参数同上 |
| GET | `/api/v1/bi/data-quality` | 数据质量看板，参数同上 |

所有 BI 端点为 rule-based JPA 聚合（非真实数仓）。recruiter 只能看自己 owner_hr_id 范围；manager/admin 看全局（未按团队细分）。

### OfferController（3 个端点）

路径 `/api/v1/offers`，与 PipelineController 的 `/api/v1/pipeline/{jobId}/candidates/{candidateId}/offer` 不同——OfferController 是独立资源路径，负责 Offer 的审批流转；PipelineController 下的 offer 是 pipeline 阶段的 Offer 数据保存。

| 方法 | 路径 | 说明 |
|------|------|------|
| POST | `/api/v1/offers` | 创建 Offer，请求体 `{ candidateId, jobId, salary?, startDate?, remark? }` |
| POST | `/api/v1/offers/{id}/withdraw` | 撤回 Offer |
| POST | `/api/v1/offers/{id}/approve` | 审批通过 Offer |

Offer 已持久化至 DB（OfferRecord 表），审批流为简化版本（approve 直接通过，无多级审批）。

### AuditLogController（1 个端点）

API.md 在系统治理一节提了"审计日志"，但实际有一个独立 Controller：

| 方法 | 路径 | 说明 |
|------|------|------|
| GET | `/api/v1/admin/audit-logs` | 审计日志列表，ADMIN only。参数 `?page=0&size=20&actorId=&action=&targetType=` |

审计日志持久化至 DB（Flyway V14 — audit_logs 表）。

### DispositionController（2 个端点）

API.md 未单独列出候选人处置端点：

| 方法 | 路径 | 说明 |
|------|------|------|
| POST | `/api/v1/candidates/{candidateId}/disposition` | 创建处置记录，请求体 `{ reason, intoPool?, nextContactAt? }` |
| GET | `/api/v1/candidates/{candidateId}/disposition` | 查询处置记录（返回最近一条） |

已持久化至 DB（Flyway V14 — candidate_disposition 表）。

## 已知响应字段不一致

以下端点的响应字段是 snake_case（Java 手写 Map 的 key，未通过 Jackson 序列化），与正文 camelCase 风格不统一：

- **通知**（NotificationController）：`is_read`、`created_at`、`per_page`、`unread_count`
- **处置**（DispositionController）：`candidate_id`、`into_pool`、`next_contact_at`、`created_at`
- **审计日志**（AuditLogController）：`actor_id`、`actor_name`、`target_type`、`target_id`

前端 api.ts 已对这些端点做适配。后续重构可以考虑统一为 camelCase。

## 三个前端标注未实现的接口

`frontend/src/lib/api.ts` 中有 3 个方法标记为"Java 端暂未实现"：

- `updateCandidateProfile` — 更新候选人资料（PATCH `/api/v1/candidates/{id}`）
- `clarifyJob` — 澄清岗位描述（POST `/api/v1/jobs/{id}/clarify`）

这些端点在 Java 后端尚未实现，目前前端调用会收到 404。

## 从 Flask 到 Java 的 API 迁移指南

如果之前对接过 Flask 旧版的 API，需要注意以下变更：

### 基础路径变更
- Flask：`/api/`（无版本号）
- Java：`/api/v1/`（带版本号）

### 命名风格变更
- Flask：snake_case（如 `resume_json`、`created_at`）
- Java：camelCase（如 `resumeJson`、`createdAt`）
- **例外**：通知、处置、审计日志三个端点仍为 snake_case（详见"已知响应字段不一致"）

### 极速信封变更
- Flask：各端点自定义返回格式
- Java：统一 `ApiResponse<T>` 信封 `{ code, message, data, timestamp }`

### 认证方式变更
- Flask：Session/Cookie 认证
- Java：JWT Bearer Token（8h 过期，`Authorization: Bearer <token>`）
