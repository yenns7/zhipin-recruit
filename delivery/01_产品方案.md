# 智聘产品方案

> **版本**: 1.0.0 | **关联文档**: 02_技术架构.md（技术实现）、05_验收与试点说明.md（已知限制）

## 系统定位

智聘是一个面向招聘团队的协作系统，覆盖从"提出招聘需求"到"候选人入职"的全流程。核心价值是让招聘专员、经理、面试官、管理员在同一个平台上看到同一套数据，减少线下沟通和表格传递。

## 四角色与权限矩阵

### 角色总览

权限升序：`interviewer < recruiter < manager < admin`

| 功能模块 | 面试官 (interviewer) | 招聘专员 (recruiter) | 招聘经理 (manager) | 管理员 (admin) |
|---------|---------------------|---------------------|-------------------|---------------|
| 岗位管理 | — | 创建/编辑/关闭/恢复自己负责的岗位 | 创建/编辑/关闭/恢复全部岗位 | 查看全部 |
| 候选人管理 | — | 上传简历/改派/处置自己负责的候选人 | 全部候选人（改派/处置） | 查看全部 |
| Pipeline 看板 | — | 移动/修正/回退/查看历史 | 同上（可跨岗位） | 查看全部 |
| 面试 | 查看被分配的任务/提交反馈/查看历史 | 安排面试/查看反馈 | 查看全部面试数据 | 查看全部 |

| AI 助手 | 对话查询 | 对话查询 | 对话查询 | 对话查询 |
| 人才地图 | — | 创建/编辑目标公司列表 | 创建/编辑 | 查看全部 |

| 审计日志 | — | — | — | 查看 |
| 系统治理 | — | — | — | 参数切换（demo 壳层） |

### 各角色详细说明

**招聘专员（recruiter）**：日常操作用户。上传简历、管理候选人、推进流程、安排面试、查看自己范围内的 BI 数据。只能看到自己负责的岗位和候选人。

**招聘经理/负责人（manager）**：团队管理者。查看团队看板、跨岗位漏斗、所有候选人（不限于本人负责）、专员归因分析。可以创建岗位和需求、做流程修正。demo 阶段 BI 范围是"全局"，不是按团队细分（见限制）。

**面试官（interviewer）**：执行面试的人。查看自己被分配的面试任务、提交面试反馈、查看面试历史。只能看到和自己相关的数据，不能创建岗位或管理候选人。

**管理员（admin）**：系统管理者。用户治理（创建/编辑/重置密码）、查看审计日志、管理系统参数。权限层级最高，能看所有数据。

## 核心业务流程

以下流程用文字描述，每条线对应一个主要操作路径：

### 主线：岗位→候选人→面试→Offer

1. **创建岗位**：招聘专员或经理创建岗位（填写 title + JD 文本），岗位状态为 active。
2. **提出招聘需求**（可选）：如果需要正式编制，创建 recruitment demand，关联岗位。
3. **获取候选人**：两种入口——上传简历（multipart，支持批量），或从 BOSS 直聘导入（demo-stub）。简历上传后自动进入异步解析，LLM 抽取出姓名/邮箱/技能等结构化信息。
4. **匹配与加入流程**：对候选人做岗位匹配（按技能/经验打分），匹配通过后自动加入 pipeline，初始阶段为 ai_screen。
5. **Pipeline 流转**：候选人沿 `pending → ai_screen → business_review → interview → offer → onboarded/rejected` 阶段推进。每个阶段有移动、修正、回退操作。
6. **面试**：在 interview 阶段，专员安排面试（指定面试官/时间/地点）。支持 AI 面试（LLM 生成题目、评分），也支持人工提交反馈。
7. **Offer**：面试通过后进入 offer 阶段，创建 Offer 记录（薪资/入职日期），可发起审批流转式。
8. **入职/淘汰**：最终落定为 onboarded 或 rejected。

### 辅线

- **人才地图**：专员或经理创建目标公司列表，记录竞品公司的人员信息。
- **AI 助手**：对话式查询招聘进度。SSE 流式响应，8 种事件类型。写操作生成 confirm-first 确认卡，不真实执行。
- **BI 看板**：概览页展示活跃岗位数、候选人总数、已解析数、各维度趋势。8 个细分维度（漏斗/渠道质量/面试问责/管理者预警/需求健康/简历消耗/数据质量）。

### 非主流程

- **通知中心**：系统级通知（候选人处置、流程变更等标记已读/未读）。
- **审计日志**：管理员查看关键操作记录。
- **系统治理**：demo 壳层，可切换 audit.manualReviewEnabled 等参数。

## 与 Flask 旧版的关系

Flask 版（`backend/` 目录）是最初的技术验证原型，前后端同源托管，使用 Python Flask + Jinja2 模板。Java 版（`rebuild/backend-java/`）是目标架构，Spring Boot 3.2 + React 18 前后端分离。两个版本独立部署，数据库不共用。

这次联调改造完成了从前端到 Java 后端的全部 API 迁移。Flask 旧版的 API 契约是 snake_case，Java 版统一为 camelCase。前后端 87 个页面/组件文件和 types 定义已全部适配。

Java 版上线后 Flask 版不再维护。

## 关键产品决策说明

### 为什么 BI 不做实时数仓而用 JPA 聚合

demo/试点阶段数据量小（预估 < 10 万条记录），JPA 聚合查询快、零运维成本。生产阶段需要接入实时数仓（如 ClickHouse）时，BI Controller 接口契约不变，只替换实现层。

### 为什么 AI 助手写操作只出确认卡

避免 AI 幻觉导致误操作。确认卡模式让用户在执行前二次确认，是产品设计层面的安全护栏。后续可以升级为"确认后真实执行"。

### 为什么 Offer 审批是简化版

当前只有 approve 直接通过，无多级审批。试点阶段团队规模小（< 50 人），简化审批链降低复杂度。生产阶段可按需扩展为多级审批流程。
